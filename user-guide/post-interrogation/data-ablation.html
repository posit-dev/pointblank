Data Ablation

A validation tells you which rows of a table fail its checks. If the table is training data for a model, the next question is whether those rows actually matter: does removing them make the model better, worse, or no different? Data ablation answers that by experiment. The model is trained on the full table and on versions of it with the failing rows removed, and each version is scored on the same held-out data. Pointblank’s Ablation class runs that experiment from an interrogated validation and reports the effect of each step’s rows.

Removing rows changes the model even when the rows were perfectly good, since there’s less data to learn from. So each version is also compared to a control, which removes the same number of rows at random. A step whose rows are really a problem does better than its control, and a step whose rows are good data does worse.

This article uses scikit-learn for the model, so you’ll need it installed (pip install "pointblank[ml]" installs it along with Pointblank) to run the examples. An ablation doesn’t depend on it: the model is just a function that you write.

The Data and the Model

The nycflights dataset has a row for each flight that left New York City airports in 2013. We’ll train a model to predict a flight’s air_time (in minutes) from its distance (in miles) and the month and hour it left. Here we take 6,000 flights, keeping 2,000 of them aside as the held-out data for scoring the model. The origin airport isn’t used by the model, but we’ll use it later to look at groups of flights.

import json

import polars as pl

flights = (
    pb.load_dataset(dataset="nycflights")
    .drop_nulls("air_time")
    .select("month", "hour", "origin", "distance", "air_time")
    .sample(n=6000, seed=23)
)

holdout = flights.tail(2000)

To know what the right answers are, we’ll add two problems to the other 4,000 flights. One flight in every 50 has its air time recorded in hours rather than minutes, and one in every 33 has a missing distance recorded as 0:

train = (
    flights.head(4000)
    .with_row_index("row")
    .with_columns(
        air_time=pl.when(pl.col("row") % 50 == 7)
        .then(pl.col("air_time") / 60)
        .otherwise(pl.col("air_time")),
        distance=pl.when(pl.col("row") % 33 == 4)
        .then(0)
        .otherwise(pl.col("distance")),
    )
    .drop("row")
)

Writing the evaluate Function

An ablation needs a function that trains the model on a version of the training table and scores it. Pointblank calls the function with the table as its first argument (the same type of table as the validation’s data, a Polars DataFrame here) and a seed= keyword. It returns the score, or a dictionary of scores if there’s more than one:

from sklearn.ensemble import RandomForestRegressor
from sklearn.metrics import mean_absolute_error, r2_score

features = ["month", "hour", "distance"]


def evaluate(train, *, seed):
    model = RandomForestRegressor(
        n_estimators=50, min_samples_leaf=5, random_state=seed, n_jobs=-1
    )
    model.fit(train.select(features).to_numpy(), train["air_time"].to_numpy())

    predicted = model.predict(holdout.select(features).to_numpy())
    actual = holdout["air_time"].to_numpy()

    return {
        "mae": mean_absolute_error(actual, predicted),
        "r2": r2_score(actual, predicted),
    }

There are a few things to keep in mind when writing this function:

  • the held-out data is fixed: it’s the yardstick for every version of the training table, so it’s never ablated
  • the function should give the same result each time it’s called with the same table and seed, so use the seed for any randomness in training (here, the forest’s random_state=)
  • the function can also take a variant= keyword, which gets an AblationVariant describing the version of the table being evaluated (its id, the steps whose rows were removed, and the number of rows removed)

Planning the Ablation

An Ablation is built in the same way as a validation: you add variants with its methods, and nothing is evaluated until you call Ablation.run(). The Ablation.drop_each() method adds a variant for each step, removing the rows that failed it, and Ablation.drop_all() adds one that removes the rows that failed any step (the failing set from Validate.get_sundered_data()).

The model is scored on the mean absolute error ("mae"), so lower is better. The Ablation.plan() method shows what the run will do, without evaluating anything:

ablation = (
    pb.Ablation(
        validation,
        evaluate=evaluate,
        metric="mae",
        higher_is_better=False,
        label="Air time model",
    )
    .drop_each()
    .drop_all()
)

The report has a row for each variant. The mae column has the mean and standard deviation of the metric over the repeats, and the change from the full table. The Δ vs random column is the main result: the mean difference between the variant and its control, with its interval and a verdict. A variant helps if it does better than its control, hurts if it does worse, and is inconclusive if the difference could be down to chance.

Here, the results match what we know about the data:

  • removing the flights with air times in hours (step 1) helps a lot, more than removing the same number of random flights
  • removing the flights with a zero distance (step 2) makes no clear difference: the problem is real, but it doesn’t measurably affect this model
  • removing the flights longer than 2,500 miles (step 3) hurts: they’re good data, and without them the model can’t predict the long flights in the held-out data
  • removing every failing row helps, but less than step 1 alone, because it includes the rows from step 3

Each version and its control are evaluated with the same seeds, and the differences are taken between runs with the same seed. This pairing means that the variation from the seed itself (here, the randomness in growing the forest) mostly cancels out.

A step’s variant shows the effect of its rows on their own, but the steps of a validation are used together, and their rows overlap. The Ablation.drop_all_but_each() method asks what each step adds to the others: for each step, it adds a variant that removes the rows failing every other step. The example of Ablation.drop_all_but_each() has a step that is redundant.

Removing Groups of Rows

The variants don’t have to come from the steps. The Ablation.drop_groups() method adds a variant for each value of a column, removing the rows with that value. This shows whether some part of the data (a source, a region, a period) is worse than the rest, which a validation can’t always say. Here’s an ablation that removes the flights from each of the three airports:

by_origin = (
    pb.Ablation(
        validation,
        evaluate=evaluate,
        metric="mae",
        higher_is_better=False,
        label="Air time model",
    )
    .drop_groups("origin")
    .run()
)

Sweeping a Threshold

A step’s variant tests one setting of its check, but the setting itself is often the question: is 2,500 miles the right limit, or would a higher one do better? The Ablation.sweep_step() method adds a variant for each of a list of values of one of a step’s parameters, each removing the rows that fail the step with that value. Here’s the limit of step 3 at four values:

by_limit = (
    pb.Ablation(
        validation,
        evaluate=evaluate,
        metric="mae",
        higher_is_better=False,
        label="Air time model",
    )
    .sweep_step(3, "value", [1500, 2000, 2500, 3000])
    .run()
)

The variants of a sweep are a group of their own in the report, and below the table, a curve shows the change from the full table at each value, with a dashed line for the controls (removing as many random rows). The lower the limit, the more long flights are removed and the worse the model gets. Even a limit of 3,000 miles, which only removes the seven flights to Honolulu, hurts. No limit helps, so this check shouldn’t be used to clean the data at all.

A check whose limit is a model’s score is the same question: a score is a matter of degree, and where to draw the line is a choice. A Validate.col_vals_scored() step (see Scored Validation) gives each row a score and keeps the scores. The Ablation.sweep_score() method then removes more and more of the rows with the highest (or lowest) scores, whatever the step’s own bound. Here, the score of a flight is the average speed implied by its distance and air time, which is far too high for the flights with their air times in hours:

def speed(batch):
    return [row["distance"] / (row["air_time"] / 60) for row in batch]


scored_validation = (
    pb.Validate(data=train, tbl_name="flights_train")
    .col_vals_scored(
        columns=["distance", "air_time"],
        scorer=speed,
        max_val=600,
        brief="Implied speed is at most 600 mph",
    )
    .interrogate()
)

by_speed = (
    pb.Ablation(
        scored_validation,
        evaluate=evaluate,
        metric="mae",
        higher_is_better=False,
        label="Air time model",
    )
    .sweep_score(1, quantiles=[0.01, 0.02, 0.03, 0.05, 0.1, 0.2])
    .run()
)

Each variant removes a share of the rows with the highest scores (the step has only a max_val=, so it’s the highest that are removed; remove="lowest" would remove the lowest instead). A sweep can also use the values of a column of the table as the scores (sweep_score("column_name")), or cutoffs on the scale of the scores rather than shares of the rows (values=).

Injecting Defects

The variants so far remove rows that a check flags, which asks whether the flagged rows hurt the model. The opposite question is just as useful: if a defect got into the data, how much would it hurt? The Ablation.inject() method answers it by adding the defect to clean rows (those that fail no step) and evaluating the corrupted table. The defect can be one of four kinds:

  • "null": the values of a column are made missing
  • "shuffle": the values of a column are moved between rows, so each is a valid value in the wrong row
  • "truncate": text values are cut to half their length
  • "duplicate": rows are copied

or a function, which is applied to the values of a column. Here, the defect is the problem that step 1 catches, air times in hours, made by a function that divides the air time by 60:

injected = (
    pb.Ablation(
        validation,
        evaluate=evaluate,
        metric="mae",
        higher_is_better=False,
        label="Air time model",
    )
    .inject(lambda minutes: minutes / 60, step=1, name="hours", rates=[0.01, 0.02, 0.05, 0.1])
    .run()
)

Each rate is a share of the rows to corrupt, and each is a variant. The rows corrupted at a rate include those at the lower rates, so the curve shows the same defect getting worse. Since no rows are removed, there’s no control: each variant is compared with the full table. Even 1% of the flights in hours makes the error almost a minute larger, and the harm grows steadily with the share.

The step= says which step checks for the defect (and its column is the one corrupted, unless column= says otherwise). The table must be a Polars, pandas, or PyArrow table, as the defect is made in memory, and the injected rows are the same in every repeat (they’re chosen from the ablation’s seed=).

Suggesting Thresholds

A step’s thresholds say how many failing rows are too many, but the right number depends on how much the failures cost. With a curve like the one above, that can be worked out: the Ablation.suggest_thresholds() method fits a line through the harm of each injected defect against the share of rows that fail its step, and gives the share at which the harm reaches a tolerance= (in the units of the metric):

injected.suggest_thresholds(tolerance=1)
{1: Thresholds(warning=0.005, error=0.01, critical=None)}

If the model can lose at most a minute of mean absolute error, step 1 should give an error once 1% of its rows fail (with a warning at half that). The suggestions are dictionaries of Thresholds by step, ready for the thresholds= of the steps. A step whose defect doesn’t clearly hurt the model, or that doesn’t catch its defect (a shuffled distance, for example, is still greater than zero), gets no suggestion, with a warning that says why.

Sharing the Effect Among the Steps

Removing every step’s rows has an effect, but the steps’ rows overlap and work together, so their effects on their own don’t add up to it. The Shapley value of a step is its fair share of the whole effect: its average effect when it’s added to every combination of the other steps. The Ablation.shapley() method adds a variant for each combination that’s needed (reusing those already in the ablation), and the report shows a Shapley value for each step:

shares = (
    pb.Ablation(
        validation,
        evaluate=evaluate,
        metric="mae",
        higher_is_better=False,
        label="Air time model",
    )
    .shapley()
    .run()
)

A Ready-Made evaluate Function

Many evaluate functions for tabular models are much the same: pick the features, encode them, fit a model, and score it on the held-out data. The ablation.sklearn_evaluator() function makes one from the held-out data and the target. By default it fits a histogram-based gradient boosting model, which handles missing values and string features, and scores it with "r2" for a regression (or "accuracy" for classification). Any scikit-learn scorers can be used instead:

    holdout,
    target="air_time",
    features=["month", "hour", "distance"],
    scoring=["neg_mean_absolute_error", "r2"],
)

boosting = (
    pb.Ablation(
        validation,
        evaluate=evaluate_boosting,

The scorers of scikit-learn are such that higher is better (which is why the mean absolute error is negated), so the default higher_is_better=True is the right one here. With this model, removing the flights with a zero distance helps too. Whether a problem in the data matters depends on the model, which is why an ablation is worth running with the model that will be trained on the data. Pass estimator= to use another model or pipeline: it’s cloned for each evaluation, with its random_state set to the seed.

Every value in this report has a standard deviation of ± 0.000, since the gradient boosting model gives the same result whatever its seed. The repeats matter most with a model that’s random itself, like the random forest, whose results vary from seed to seed. Either way, the Ablation.check_determinism() method (see below) checks that the same seed gives the same result.

Running Larger Ablations

The ablations here make a few dozen evaluations, but with a model that takes minutes to train, a run can take hours. A few things help with that.

Before a long run, it’s worth checking that the evaluate function uses its seed for all of its randomness, since the paired comparisons rely on it. The Ablation.check_determinism() method evaluates the full table twice with the same seed, and warns if the results differ:

ablation.check_determinism()
True

The max_workers= parameter of Ablation.run() makes the evaluations in parallel. They run in threads by default, which suits models that release Python’s lock while they train (most of those in compiled libraries do), and executor="process" runs them in separate processes instead (this needs an evaluate function defined at the top level of a module). The random forest here already uses every core with n_jobs=-1, so it wouldn’t gain much.

The cache= parameter of Ablation keeps each evaluation’s result in a directory, so that a run that stops partway through (or a run with an added variant) only makes the evaluations it doesn’t already have. A result is found again only for the same data, the same rows removed, and the same seed, so a change to the table gives new evaluations. A change to the model doesn’t, since Pointblank can’t see inside the evaluate function, so give it an evaluate_version= that you change along with the model:

ablation = pb.Ablation(
    validation,
    evaluate=evaluate,
    metric="mae",
    higher_is_better=False,
    cache=".ablation-cache",
    evaluate_version="random forest, 50 trees",
).drop_each()

ablation.run(max_workers=4)

The report says how many of the evaluations came from the cache.

When the training pipeline loads the data itself (from a database, say, or a file that’s too large to copy for each version), pass_as="row_index" gives the evaluate function the list of the numbers of the rows to keep (counting from 0, in the order of the table) instead of the table. A list can be sent to another process, so this also makes executor="process" work for any kind of table:

def evaluate_rows(rows, *, seed):
    return evaluate(train[rows], seed=seed)


pb.Ablation(
    validation,
    evaluate=evaluate_rows,
    metric="mae",
    higher_is_better=False,
    pass_as="row_index",
).drop_each().run()

With a list of rows, the defects of Ablation.inject() can’t be passed on, so they need the default pass_as="table".

Evaluating Somewhere Else

Sometimes the model can’t be trained in the Python session that has the validation: it’s trained on a cluster, by another team, or in another language. The Ablation.export() method writes every version of the training table that a run would evaluate to a directory, as Parquet files, along with a manifest.json that lists each evaluation (its version of the table, its file, and its seed) and a results_template.csv to fill in. With format="indices", it writes the row numbers that each version removes instead, for a table that’s too large to copy.

Here, the evaluations are made by reading the files back and calling the same evaluate function, but any process that writes a row of metrics for each evaluation would do:

import tempfile
from pathlib import Path

plan = pb.Ablation(
    validation, metric="mae", higher_is_better=False, repeats=3
).drop_each(steps=1)

directory = plan.export(Path(tempfile.mkdtemp()) / "air-time-ablation")

manifest = json.loads((directory / "manifest.json").read_text())

results = pl.DataFrame(
    [
        {
            "variant": run["variant"],
            "repeat": run["repeat"],
            "seed": run["seed"],
            **evaluate(pl.read_parquet(directory / run["file"]), seed=run["seed"]),
        }
        for run in manifest["runs"]
    ]
)

results.write_csv(directory / "results.csv")

The sweeps, inject, and shapley are strategies too, with their arguments by name (e.g., - sweep_step: {step: 3, param: value, values: [1500, 2000, 2500, 3000]} or - inject: {corruption: "null", step: 2}). In YAML, a defect must be one of the four kinds by name, not a function. The holdout: is a data source like tbl: (e.g., holdout: flights_holdout.parquet), which yaml_ablation(..., holdout=...) can replace with a table, as set_tbl= does for tbl:.

The block is ignored by yaml_interrogate(), so the same file can be used for validating the data, and yaml_to_python() writes out the equivalent Python code, ablation included.

How the Comparisons Are Made

For each variant, the difference from its control is computed for each repeat, and the report shows the mean of these differences with a paired t-interval (95% by default, set with conf_level=). The p-values are adjusted for the number of variants with the Holm method, and the verdicts use the adjusted p-values: a variant helps or hurts only if its adjusted p-value is below 1 - conf_level. You can turn off the adjustment with adjust=None. Injected defects remove no rows, so they’re always compared with the full table, and the Shapley values have intervals and p-values of their own (from the values of each repeat), adjusted for the number of steps.

With fewer than three repeats, there’s too little data for a useful interval, so the report gives no verdicts (and Ablation warns about this). More repeats give narrower intervals, at the cost of more evaluations.

The t-interval assumes that the differences are roughly normal, which a few outlying repeats (a model that sometimes fails to converge, say) can make untrue. With ci="bootstrap", the intervals and p-values come from 4,000 resamples of the repeats instead: the interval has the middle 95% of the resampled mean differences, and the p-value is the share of them on the other side of zero. The bootstrap assumes nothing about the distribution of the differences, but it needs more repeats (with fewer than 10, its intervals are too narrow, and Ablation warns about this). The resamples are made from the seed=, so the results are the same each time.

A few other options are worth knowing about:

  • control=None compares variants only to the full table, which saves evaluations but leaves the effect of removing any rows mixed in with the effect of removing these rows
  • control=pb.ablation.Stratified("origin") (see ablation.Stratified) draws the random rows of each control from each group in proportion to its size, so that a control doesn’t take more rows from one group than another by chance (worth using when the groups matter to the model, like the classes of a classification target)
  • max_removed= (by default 0.5) sets the share of rows above which a variant gives a warning, since a version of the table missing most of its rows is a different dataset rather than an ablation of this one
  • duplicates= and duplicates_order_by= say which copy of a duplicate row a Validate.rows_distinct() step should keep (by default the first one, as with Validate.get_row_flags()); see Sundering Validated Data for more on these

Only steps that check rows can be used in an ablation. Steps that check the table as a whole (like Validate.col_exists()), inactive steps, and steps using a pre= function that isn’t marked with row_preserving() are left out, and the plan and report have a note for each step that couldn’t be used.

Conclusion

A validation can say which rows break its rules, but only an experiment can say whether those rows hurt the model trained on them. An Ablation runs that experiment with controls, repeats, and intervals, so you can find the checks that are worth enforcing, the ones that don’t matter, the ones that are redundant, the ones that remove good data, and where to set their limits. Injecting defects shows how much a problem would cost (and gives thresholds to match), and Shapley values share the effect of the whole cleaning fairly among the steps. It works with any model that you can wrap in an evaluate function (or train elsewhere, with export() and load_results()), and with any validation whose steps check rows.
