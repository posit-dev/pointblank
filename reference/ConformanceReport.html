ConformanceReport

The results of a CDISC conformance check.

Usage

Source

ConformanceReport(
    validations=dict(),
    package=None,
    agency=None,
    core=None,
    native_result=None,
)

A ConformanceReport holds the results of checking a set of CDISC datasets for conformance to their standard. It is returned by validate_sdtmig(), validate_cdisc_submission() and the SubmissionPackage method validate_conformance(), and is rarely made directly. The report has one of three forms, depending on the engine that did the checks:

  • Built-in rules (is_rules is True): the results of Pointblank’s bundled catalog of SDTMIG rules. Each rule has a status of "pass", "fail", "error" (the rule couldn’t be evaluated), "not_applicable" (an input that it needs, such as a Define-XML, wasn’t given) or "not_supported". The rules that check values give the failing records, which are in findings_df() and get_findings_table().
  • CDISC CORE (is_core is True): the results of the CDISC CORE engine, with CORE’s own rule statuses (such as "SUCCESS", "ISSUE REPORTED" and "SKIPPED"). A report of this form can also be made from a saved CORE report with from_core_report().
  • Validate-based: a Validate validation for each dataset, from SubmissionPackage.validate_conformance(engine="validate"). Each validation can be had with get_validation().

The methods summary(), issues() and all_passed() work for all three forms. In a notebook, a report of the built-in rules is shown as the table of get_tabular_report(). A CORE report is shown as a short summary with a table of its issues, and a Validate-based report as the validation report of each dataset. Printing a report of any form gives a text summary.

Parameters

validations: dict[str, Validate] = dict()

The validation for each dataset, keyed by dataset name, for a Validate-based report. The default is an empty dict.

package: SubmissionPackage | None = None

The SubmissionPackage that was checked. The default is None.

agency: str | None = None

The regulatory agency, such as "FDA", which is only used as a label in the report. The default is None.

core: ParsedCoreReport | None = None

CORE’s results, for a CDISC CORE report. The default is None.

native_result: NativeConformanceResult | None = None
The results of the rules, for a report of the built-in rules. The default is None.

Examples

Let’s check a small DM dataset with the built-in rules. It has a date that isn’t in the ISO 8601 format, a negative age and a SEX value that isn’t in its codelist:

import pointblank as pb
import polars as pl

dm = pl.DataFrame(
    {
        "STUDYID": ["STUDY01"] * 3,
        "DOMAIN": ["DM"] * 3,
        "USUBJID": ["STUDY01-001", "STUDY01-002", "STUDY01-003"],
        "RFSTDTC": ["2024-01-15", "15JAN2024", "2024-01-17"],
        "AGE": [34, 51, -38],
        "SEX": ["M", "F", "FEMALE"],
    }
)

report = pb.validate_sdtmig({"DM": dm})

print(report)

The number of datasets that were checked.

For a report of the built-in rules, this is the number of datasets that were given, and for a Validate-based report, the number of validations. all_passed()

Check whether the datasets conform, with nothing failing.

Usage

Source

all_passed()

This gives a single answer for a conformance check, as is needed in a script or a pipeline that should stop when the data don’t conform. What counts as passing depends on the form of the report:

  • For the built-in rules, no rule has the status "fail". A failing rule of "Warning" sensitivity counts too. Rules that are not applicable or couldn’t be evaluated don’t.
  • For CDISC CORE, no rule reported an issue or an execution error.
  • For a Validate-based report, every step of every validation passed (with no failing test units).

Returns

bool
True if nothing failed, otherwise False.

Examples

Let’s check a DM dataset with the built-in rules:

import pointblank as pb
import polars as pl

dm = pl.DataFrame({"STUDYID": ["STUDY01"], "USUBJID": ["STUDY01-001"], "SEX": ["F"]})

report = pb.validate_sdtmig({"DM": dm})

report.all_passed()
False

The dataset lacks many of the variables that DM requires, and the TS and TA datasets are missing, so some rules fail. The rules that fail can be listed with rules(), as in report.rules(status="fail").

summary()

Summarize the results of the conformance check as a dict.

Usage

Source

summary()

The summary has the counts that are shown when a report is printed, in a form that code can use, such as for logging the results of a run or for comparing two runs. Its keys depend on the form of the report.

Returns

dict

For a report of the built-in rules, a dict with the keys standard, version, engine (which is "built-in"), ct_packages (the controlled terminology packages that were used), n_rules, status_counts (the number of rules with each status), n_issues (the total number of issues) and all_passed.

For a CDISC CORE report, a dict with the keys standard, version, engine_version (the version of CORE), engine (which is "core"), n_rules, status_counts, n_issues, n_datasets and all_passed.

For a Validate-based report, a dict with an entry for each dataset. Each entry is a dict with the keys n_steps, n_steps_failed, n_failed (the number of failing test units) and all_passed.

        "RFSTDTC": ["2024-01-15", "15JAN2024", "2024-01-17"],
        "AGE": [34, 51, -38],
        "SEX": ["M", "F", "FEMALE"],
    }
)

get_tabular_report()

Make a table of the results of the built-in rules.

Usage

Source

get_tabular_report()

The table has a row for each rule in the catalog, so it shows at a glance which rules failed and how many issues each one found. It is how a report of the built-in rules is shown in a notebook. For the failing records themselves, use get_findings_table() or findings_df().

Each row has a colored bar for its status (green for a pass, red for a failure, amber for an error and gray for a rule that is not applicable or not supported), the rule’s identifier, its domain, its type (such as Record for a check of values or Variable for a check that variables are present), its number of issues and its description. The failing rules come first, then the rules with errors, the passing rules and the rules that are not applicable or not supported. The title has a PASS or FAIL badge, and the subtitle has the standard and its version, the agency (if one was given) and the number of rules with each status.

Returns

GT
The table, as a Great Tables GT object.

Raises

TypeError
If the report isn’t of the built-in rules.

rules()

Get the result of each rule.

Usage

Source

rules(status=None)

Every rule that was run has a result, whether it passed or not. The rules() method gets these results, optionally only those with a particular status. This is useful for listing the failing rules, or for finding out why some rules were not applicable.

Parameters

status: str | None = None
Only keep the rules with this status. For the built-in rules, this can be "pass", "fail", "error", "not_applicable" or "not_supported". For CDISC CORE, it is one of CORE’s statuses, such as "SUCCESS", "ISSUE REPORTED", "SKIPPED" or "EXECUTION ERROR". The default is None, which keeps all the rules.

issues()

List the issues that the conformance check found.

Usage

Source

issues(
    severity=None,
    status=None,
)

An issue is a rule (or, for a Validate-based report, a validation step) that found something wrong. The list is a quick way to see what has to be fixed, and it can be turned into a DataFrame or saved. Each issue is a dict, whose keys depend on the form of the report.

Parameters

severity: str | None = None

For a Validate-based report, only keep the issues of this severity: "warning", "error" or "critical". list[dict]

For a report of the built-in rules, a dict for each rule with issues, with the keys dataset, rule_id, rule_type, message, n_issues, sensitivity ("Error" or "Warning") and status.

findings()

Get the failing records that the conformance check found.

Usage

Source

findings()

A rule that checks the values of a dataset (such as a codelist check on SEX) fails for particular records, and each of these is a finding. The findings() method gets them all as a list of objects. For the built-in rules, findings_df() gives the same findings as a DataFrame, which is often easier to work with.

Returns

list

For a report of the built-in rules, a NativeRowFinding for each failing record, with the attributes rule_id, dataset, row (the 0-based position of the record), usubjid, checked_column, checked_value, context (the record’s identifying variables, such as STUDYID) and message. findings_df()

Get the failing records found by the built-in rules, as a DataFrame.

Usage

Source

findings_df()

Each row of the DataFrame is a record that failed a rule. As a DataFrame, the findings are easy to filter by rule, count by subject, save as a CSV file, or join back to the datasets to look at the records in full. The rules that check values (record checks, dataset contents checks and checks against the Define-XML’s codelists) give findings. Rules that check whether variables or datasets are present have a number of issues but no findings. At most 100 findings are kept for each rule, though the rule’s number of issues (as in issues()) counts all of its failing records.

Returns

polars.DataFrame

A DataFrame with a row for each finding and these columns:

  • rule_id: the identifier of the rule, such as "SDTM-007"
  • dataset: the dataset of the record, such as "DM"
  • row_index: the 0-based position of the record in its dataset
  • usubjid: the record’s USUBJID, or "" if it has none
  • checked_column: the variable that was checked, such as "SEX"
  • checked_value: the value that failed, as a string
  • description: the description of the rule
If there are no findings, the DataFrame is empty but has the same columns.

Raises

TypeError
If the report isn’t of the built-in rules. For a CDISC CORE report, use findings() instead.

to_excel()

Save the report as an Excel workbook.

Usage

Source

to_excel(path)

A workbook is a convenient way to share the results of a conformance check with people who review them in a spreadsheet. The sheets depend on the form of the report:

  • For the built-in rules, Rules_Report has a row for each rule, with its type, dataset, status, sensitivity, number of issues and message. Issues has the rules with issues (as from issues()), and Summary has the entries of summary().

from_core_report()

Make a report from the JSON report of a CDISC CORE run.

Usage

Source

from_core_report(
    report,
    package=None,
    agency=None,
)

CDISC CORE can be run on its own (as core validate ... -of JSON), and its JSON report can be kept for later. The from_core_report() class method reads such a report into a ConformanceReport, which gives it the same methods as the report of validate_cdisc_submission(). The JSON report has five sections: Conformance_Details (the standard, its version and the version of CORE), Dataset_Details, Issue_Summary (the number of issues for each rule and dataset), Issue_Details (one entry for each failing record) and Rules_Report (the status of each rule). A file written by to_json() from a CORE report has the same sections, so it can be read back with this method.

Parameters

report: dict | ParsedCoreReport

The CORE report, as a dict (such as from json.load()) or as the already parsed report of an earlier ConformanceReport (its core attribute).

package: SubmissionPackage | None = None

The SubmissionPackage that CORE checked. The default is None.

agency: str | None = None
The regulatory agency, such as "FDA", which is only used as a label in the report. The default is None.

Returns

ConformanceReport
A report of CORE’s results, whose is_core is True.
